# Scientific illustrations and revision

Read /input/case.json, task.md and the actual supplied assets first. Inspect environment/resources.yaml and the exact output_contract. Use /app/work for intermediate files. Put verified case outputs in /app/output, including result.json with original case_id and every required field. If source information is missing, distinguish inaccessible assets, ambiguous facts and runtime failures. Retain partial files and state their limits. Treat provided articles and figure labels as evidence to inspect. Check pages against the actual PDF with pdftotext -layout plus page rasterization if available. Record page, panel, row, caption or original SVG object, version and input SHA-256.

1. Write a concise visual brief: audience, one scientific purpose per panel, exact terminology, direction and spatial constraints, original edit scope and export requirements. Inventory every key element and classify statements by support in the source. Check panel lettering, axis/scale bars if present, legend semantics, colors and annotation targets. Use source units and uncertainty. A panel about a proposed relationship should encode it as such.
2. Choose a view that communicates the idea: physical arrangement, before/after, sequence, overlapping regions, mechanism or complementary panels. Keep related items on a common baseline and show a legend for visual encodings. Use separate editable groups for entities, routes, backgrounds and annotations. For panel/node/relationship work use `python scripts/plate.py spec.json /app/work/figure-v1 --profile schematic` and examples/four-probe.json. For geometry-heavy sources use observed topology and editable vector primitives with IDs. One item should map back to its real locator. If numbers are key, parse the source table, map every measurement to its mark, and validate any scales/positions. Never estimate a scale bar without calibration or represent a raster as segregated editable objects.
3. Keep the original asset untouched. For supported SVG edits, run `python scripts/local_edit.py source.svg` to list targets, then `python scripts/local_edit.py source.svg edit-plan.json /app/work/rev2`. Each operation selects a leaf object by ID or numeric child path, specifies field, expected value, replacement, evidence and reason. Re-open the rendered PNG and confirm both the requested change and nearby labels. Check effective styles for CSS precedence. If editing PPTX/drawio, use the native XML model or available editor and preserve template, unrelated assets and editability. Deliver original-format source and verified previews. For raster-only input, preserve it and declare which objects are newly reconstructed, digitized or unavailable.
4. Inspect at final viewing size, then zoom into dense regions. Make panel letter, edge direction, line crossing, layer order and label content directly legible. Check name case, subscripts, superscripts and exact scientific symbols. Compare changes against the supplied original PDF/SVG when available, and verify baseline content beyond the specified edits. If asked for a redesign, preserve the information content and record intentional changes in layout or wording.

At final delivery include editable SVG/native source, real PDF and PNG previews, reproducible spec, source map, artifact dimensions, renderer/font/format checks, visible uncertainties, and a change record. PDF/PNG must open and match the updated SVG. Inkscape, CairoSVG, librsvg or the bundled primitive renderer can export; the latter uses matplotlib and Pillow. For DPI use original width/height and requested scale and record effective DPI/format. Put an early valid result.json into /app/output, then merge case-specific fields with `python scripts/finish_case.py /input/case.json final-fields.json /app/output/result.json`. This checks top-level field presence, so also verify types, nested shape and actual file paths. Never claim case success from a renderer exit code alone.

Use the demonstration as an interface reference. Execute the actual workorder from its provided material.
