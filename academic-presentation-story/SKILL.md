# 学术汇报内容组织

Start with /input/case.json, task.md and actual materials. List the resources described in environment/resources.yaml. Work in /app/work and write final files to /app/output. Read the real paper and supplied deck or template before designing. Preserve both original evidence and requested specimen files. Inspect the original output_contract and deliver every required field plus original case_id. Write initial result.json early and update it after visual verification. Source citations identify exact PDF page and printed figure/panel, table field, slide/object, or file and line for independently uploaded data. Distinguish unreadable input, ambiguous evidence and export failure.

1. Turn the request into a one-sentence audience outcome and a prioritized evidence list. Assign each slide a narrative job and one falsifiable takeaway. Match reading load to time. Distinguish the core talk from backup slides. Do not put paper order on autopilot: establish the motivating question first, use the minimum method context needed to understand the figures, then tell the story through the findings and fair limitations.
2. Create a slide plan containing opening, audience, deck title, timing, one key claim, source, visual, explanation in speaker notes, outgoing transition and handoff into the next slide. Run `python scripts/story.py plan.json /app/work/story` to validate talk versus appendix time and source linkage. Keep a speaking margin within the requested budget. Name the strongest counterargument and show whether it is addressed. Put any unsupported filler into an explicit verification list.
3. Read references/design.md for the design and review procedure. First draw the intended composition by assigning the main evidence the majority of the usable area. Use real source figures or deterministic chart geometry for exact scientific facts. Keep real plots legible under projection. Use a sentence title that a reader can test against the evidence, a stable alignment grid, typography sized for the venue, meaningful color with a secondary encoding, and one main visual per slide. If a slide has no visualizable evidence, use a restrained text or equation composition instead of decorative cards. Use body slides to prove a claim. Put detail that supports narration in notes and audit detail in an appendix. Use the topic, not a fixed theme, to choose the color system.
4. Use the preinstalled presentation and PDF tooling listed in the case. The portable examples use python-pptx, Pillow and matplotlib. Use scripts/deck.py for a new deck and scripts/check_deck.py for an independent inventory/preview of supported shapes, or render final PPTX through LibreOffice, e.g. `soffice -env:UserInstallation=file:///tmp/bohrium-academic-slide --headless --convert-to pdf --outdir /app/output /app/output/figure.pptx` followed by pdftoppm. Inspect a contact sheet, then open every changed, crowded and figure-heavy slide at full size. Fix clipped text, detached legends, non-projectable contrast, distorted figures and missing data units. Keep notes and evidence in the actual PPTX. Document the renderer used and limits.
5. Deliver the slide-by-slide evidence/timing plan, a usable final deck and previews when requested, and source references. Verify every deck slide's claim and speaker notes against the plan. Read the transitions aloud on paper and eliminate repeated introductions, background that delays the evidence, and summaries that add new unsupported claims.

Write all exact task deliverables using task-required names. Run `python scripts/finish_case.py /input/case.json actual-fields.json /app/output/result.json` only after generating cited files and actual-field values. Review nested requirements and relative paths independently. Do not use demonstration material as an answer to any provided case.
